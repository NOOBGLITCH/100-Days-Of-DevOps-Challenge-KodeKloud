# Jenkins + Gitea Automated Deployment

## Overview

In this lab, we configure a Jenkins Freestyle job to automatically deploy a static website whenever a new change is pushed to the `master` branch in Gitea.

The final workflow is:

```text
Developer
   │
   │ git push origin master
   ▼
Gitea Repository
   │
   │ Webhook
   ▼
Jenkins
   │
   │ Remote Build Trigger
   ▼
nautilus-app-deployment
   │
   ▼
App Server 1 (stapp01)
   │
   │ Deploy
   ▼
/var/www/html
   │
   ▼
Apache :8080
```

# 13. Configure the Deployment Script

Go to:

**Build → Add build step → Execute shell**

Add:

```bash
#!/bin/bash

set -e

echo "Running on agent: stapp01"

sudo chown -R sarah:sarah /var/www/html

sudo rm -rf /var/www/html/*

sudo cp -r /home/sarah/web/. /var/www/html/

sudo rm -rf /var/www/html/.git

sudo chown -R sarah:sarah /var/www/html

sudo systemctl enable --now httpd

echo "Deployment completed successfully"
```

This deploys the **entire repository**, rather than copying only `index.html`.

# Good to Know

## Webhook-Triggered Deployments

* **Automatic Triggers:** Deployments can start automatically when code changes are pushed.
* **Git Hooks:** Repository events can trigger Jenkins builds.
* **Continuous Deployment:** Changes can move automatically from source control to the deployment environment.
* **Event-Driven:** The deployment process reacts to repository events instead of requiring a manual build.

## Webhook Configuration

* **Payload URL:** The webhook sends repository events to a Jenkins endpoint.
* **Authentication:** API tokens can authenticate requests between Gitea and Jenkins.
* **Event Types:** Webhooks can respond to events such as pushes, pull requests, or tags.
* **Filtering:** Webhooks can be configured to react only to required events or branches.

## CI/CD Pipeline

* **Source Control:** Jenkins retrieves the latest code from the Git repository.
* **Build:** Jenkins can compile and test the application before deployment.
* **Deploy:** The latest code is copied to the target environment.
* **Notify:** Build and deployment results can be communicated to the team.

## Jenkins Agents

* **Distributed Builds:** Agents allow Jenkins jobs to execute on remote machines.
* **Labels:** Labels such as `stapp01` allow jobs to target a specific agent.
* **Remote Workspace:** The agent's remote root directory provides the workspace used by Jenkins.
* **Dedicated Execution:** Deployment tasks can run directly on the target application server.

## Static Website Deployment

* **Document Root:** Apache serves website files from `/var/www/html`.
* **Direct Deployment:** Website files are placed directly in the document root.
* **No Subdirectory:** The application can therefore be accessed from the main URL without `/web` or another subdirectory.
* **Simple Updates:** Static files become available after deployment without requiring application compilation.

## Security Considerations

* **API Tokens:** Use API tokens for Jenkins authentication rather than exposing account passwords.
* **Credential Management:** Store Git credentials and other secrets in Jenkins Credentials.
* **Passwordless sudo:** Grant only the permissions required by the deployment process instead of unnecessarily giving broad privileges.
* **Network Security:** Restrict webhook access to trusted systems where possible.
* **Audit Logging:** Jenkins build history provides a record of deployment activity.
